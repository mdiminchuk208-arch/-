# Stage A tick and filter compatibility — independent pre-outcome assessment

**Verdict: STOP for exact frozen-v3 historical execution on OKX.** This is an evidence/readiness stop, not a strategy performance result. No new financial outcome was inspected. The 2024-10-13 00:00 UTC through 2026-10-13 00:00 UTC development period, with warmup from 2023-10-14, lacks verified historical tick/filter epochs for both `BTC-USDT-SWAP` and `ETH-USDT-SWAP`. The current public instrument records cannot be applied backward. The bounded official announcement API check below was blocked, and neither the retained OKX sources nor the checked official API documentation supply a complete historical instrument-change series.

## What the frozen contract requires

`docs/machine_strategy_v3_design/RISK_NORMALIZATION_SPEC.json` requires a verified zero-origin price lattice, source/effective publication proof known no later than the decision, and exactly one epoch covering each decision; unknown or changed epochs wait. `scripts/machine_strategy_v3_contracts.py::proven_tick_epoch` enforces `verified=true`, a source hash, source and effective proof times no later than the decision, and a unique interval. `executable_plan` rounds LONG entries down and SHORT entries up, stops strictly outside the boundary, and targets strictly inside the nearest FTA. The execution path requires the same epoch at each M15 bar's start and end, equal to the order's epoch, and requires all OHLC and order prices to lie on its lattice. The pure core checks schema and digest syntax; it does **not** authenticate archived source bytes or establish complete historical intervals. A fabricated `verified=true` row would defeat the contract rather than satisfy it.

The retained official OKX instrument responses in `docs/exchange_selection_audit_v1/evidence/okx/SOURCE_INDEX.json` (`instrument_btc`, `instrument_eth`) establish current product identities and filters: BTC tick `0.1`, lot/min size `0.01`, `ctVal=0.01 BTC`; ETH tick `0.01`, lot/min size `0.01`, `ctVal=0.1 ETH`; both linear USDT-settled SWAP with `ctMult=1`. Their retrieval time is 2026-10-12, after almost the entire frozen test window. The official `docs_main#public-data-rest-api-get-instruments` describes open/current contracts. `docs_main#public-data-websocket-instruments-channel` describes incremental notifications when `tickSz`, `minSz` or `maxMktSz` changes; it does not provide historical replay. The previously retained OKX `RESEARCH.md` and Stage-1 checkpoint already mark historical epochs unresolved. No source inspected proves historical `tickSz`, `lotSz`, `minSz`, contract value/multiplier, or all change boundaries throughout the warmup and development window.

## Bounded additional official check

On 2026-10-13 UTC, two unauthenticated GETs with `Accept-Language: en-US` and `Accept: application/json` were made through the inherited HTTPS proxy with TLS verification and no redirect follow. Their exact URLs, request/retrieval UTC, HTTP statuses, response header allowlist, raw bytes and SHA-256 are in `evidence/tick_metadata/announcement_types.receipt.json` and `evidence/tick_metadata/announcements_page_1.receipt.json`, paired with raw `.body` files. The URLs were `https://www.okx.com/api/v5/support/announcement-types` and `https://www.okx.com/api/v5/support/announcements?page=1`. Both returned HTTP 403 with Cloudflare error 1010 (`browser_signature_banned`); the bodies explicitly say not to retry. These responses contain no notice list or historical rule. This is a public-endpoint access observation, not proof that notices do not exist. The retained OKX API documentation describes the announcement endpoint, its 20-record pages, and public IP restrictions; it does not certify complete coverage for this window.

The official funding archive already recovered elsewhere in Stage A is a funding-rate series. It cannot establish price/size filters. Native M15 candles establish price observations, not exchange order constraints. This assessment makes no broader claim that OKX has no separate internal or public archive.

## Compatibility decisions

| Proposed shortcut | Assessment for exact frozen v3 |
| --- | --- |
| Backdate today's `tickSz`/`lotSz`/contract fields | Invalid: a 2026 snapshot has no proof of historical effective intervals or absence of changes. |
| Infer tick from OHLC decimal places or a GCD | Invalid: candle OHLC is a sparse sample of traded prices; several finer exchange ticks can produce identical observed decimals/GCD. Size limits and contract value cannot be derived from prices. |
| Interpolate between occasional metadata snapshots | Invalid: unobserved changes can occur between snapshots; later snapshots were unavailable to earlier decisions. Equal endpoints do not prove an unchanged interval. |
| Use an arbitrary coarse fixed grid as a conservative substitute | No guaranteed conservative qualification. Rounding changes entries, stops, targets, eligibility, fill probability, exit order and cash-stop units. A stricter grid can exclude losing fills or turn some paths into wins, so it does not bound win rate, expectancy or drawdown adversely. A coarse grid can also reject valid OHLC in the frozen execution check. |
| Label a synthetic row `verified=true` and feed it to `proven_tick_epoch` | Invalid: schema acceptance is not source authentication or effective-date proof. |

A pre-outcome **separate version** could specify an economically justified compatibility model and test it under its own qualification contract, but it must not be described as an exact frozen-v3 OKX run or as a source-verified epoch. The currently available evidence does not justify any single fixed grid as a guaranteed conservative bound on the frozen v3 financial metrics. Changes to tick rounding, size eligibility, execution treatment or decision timing can change strategy decisions; they require an explicit new version frozen before outcomes. Neither a technical policy nor a synthetic assumption may be promoted to an OKX source rule.

## Precise unblock path

Before Stage A PASS for exact frozen v3, obtain official, dated OKX source material that anchors each product's tick/lot/minimum size and contract specification at the beginning of warmup and covers every relevant change through the end of development. A complete official historical instrument-change log or a provably exhaustive dated announcement archive with effective timestamps is suitable; individual notices without a complete initial anchor and gap-free change coverage are insufficient. Retain raw bytes, URL, UTC retrieval, status and SHA-256; independently verify publication time and the rule's effective time. Build nonoverlapping per-product epochs whose `source_known_at` and effective proof were public by each decision, and verify continuous coverage across decisions and M15 execution bars. Check historical contract value/multiplier and size filters separately from the tick grid. If official historical coverage remains unavailable, keep Stage A at **STOP** for the specified exact frozen-v3 historical test. A forward-only prospective capture can establish epochs from its verified observation boundary onward, but cannot repair 2023–2026 history.
