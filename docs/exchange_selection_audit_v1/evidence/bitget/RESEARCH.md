## Product, fees and filters

Official current contract responses for `productType=USDT-FUTURES` identify both `BTCUSDT` and `ETHUSDT` as `symbolType:"perpetual"`, quote `USDT`, support margin `USDT`, and show `symbolStatus:"normal"` [bitget:BTCUSDT_instrument] [bitget:ETHUSDT_instrument]. The official Classic contract schema calls the endpoint “future contract details,” says `makerFeeRate` is “Maker rate” and `takerFeeRate` is “Taker rate,” and describes `minTradeNum` as “Minimum opening amount (base currency)” [bitget:bitget_detail_market]. Both current product payloads literally state `"makerFeeRate":"0.0002"` and `"takerFeeRate":"0.0006"`. These are public ordinary product parameters for the fee comparison. An individual account's effective API fee remains unverified; no private fee query was made. The separate VIP endpoint has `level:"1"`, `makerFeeRate:"0.00019"`, `takerFeeRate:"0.0006"`, so that conditional discount is excluded [bitget:bitget_vip_fee]. The dynamic public `/fee` page did not yield a text schedule [bitget:bitget_docs_fee2].

Current BTC filters are `pricePlace=1`, `priceEndStep=1` (price tick 0.1), `volumePlace=4`, `sizeMultiplier=0.0001`, `minTradeNum=0.0001`; ETH filters are `pricePlace=2`, `priceEndStep=1` (price tick 0.01), `volumePlace=2`, `sizeMultiplier=0.01`, `minTradeNum=0.01` [bitget:BTCUSDT_instrument] [bitget:ETHUSDT_instrument] [bitget:bitget_detail_market]. These are retrieval-time filters. The official Classic changelog exists [bitget:bitget_docs_classic_changelog], but the evidence does not reconstruct complete historical tick/filter epochs. Prospective timestamped instrument capture is feasible; backdating filters is not.

## Public data, funding and book units

Both current M15 endpoints returned native 15-minute starts and the historical endpoint returned the bar starting exactly `2024-10-13T00:00:00Z` for **both** products [bitget:BTCUSDT_m15now] [bitget:ETHUSDT_m15now] [bitget:BTCUSDT_m15old] [bitget:ETHUSDT_m15old]. The official historical-candles schema lists `15m`, maximum 200 rows and warns that an end time past a boundary can cause an extra earlier interval; its historical response is finished candles. The current candles endpoint says an empty array indicates no data and limits ordinary 15m queries to 52 days [bitget:bitget_detail_market]. The historical sentinel demonstrates a two-year path, not uninterrupted bar continuity or earliest possible history. The official download center and market docs mention historical futures candles and depth, but no archive file was retrieved [bitget:bitget_docs_download] [bitget:bitget_detail_market]. The market docs also list historical trades, mark and index candles and current OI; current OI and two recent funding rows per symbol were captured [bitget:BTCUSDT_oi] [bitget:ETHUSDT_oi] [bitget:BTCUSDT_funding] [bitget:ETHUSDT_funding]. Full OI history, trade/depth archive coverage and funding retention remain unknown.

Both product responses state `fundInterval:"8"`; the official schema calls it “Funding fee settlement cycle, hourly/every 8 hours” [bitget:BTCUSDT_instrument] [bitget:ETHUSDT_instrument] [bitget:bitget_detail_market]. Funding history uses `GET /api/v2/mix/market/history-fund-rate`, with `pageSize` maximum 100 [bitget:bitget_detail_market]. Positive and negative historical rates were observed; the payer/payee sign rule, formula/caps and platform surcharge were not verified. Funding is recorded separately from trading fees.

Two separated, 100-level documented `merge-depth` captures per symbol appear as decimal string `[price, base_quantity]` arrays in [FACTS.json](FACTS.json). BTC best bid/ask at the first sample was 83704.9/83705.0; ETH was 2532.39/2532.40. The second samples were about 30 seconds later [bitget:bitget_BTC_merge_book] [bitget:BTCUSDT_merge_book2] [bitget:bitget_ETH_merge_book] [bitget:ETHUSDT_merge_book2]. The merge-depth schema says each row is `[Price, Quantity]`; the same official Classic futures order schema calls order `size` “Amount (base coin)” [bitget:bitget_detail_market] [bitget:bitget_detail_trade]. We therefore transcribed quantities at multiplier 1 into base coin. The depth field itself lacks an explicit unit; cost scoring should retain that qualification. Additional original `orderbook` endpoint snapshots are retained as raw diagnostics, but the documented `merge-depth` captures are used for normalization. Snapshots are observations, not future fill guarantees.

## Execution and access

Official Classic REST and WebSocket docs cover public/private channels [bitget:bitget_docs_rest_api] [bitget:bitget_docs_ws_intro]. The futures order schema explicitly provides `marginMode` (`isolated`/`crossed`), `reduceOnly` (`YES`/`NO`) for one-way positions, `clientOid`, preset take-profit and stop-loss prices, and says order `size` is base coin [bitget:bitget_detail_trade]. Separate plan-order endpoints describe conditional TP/SL and reduce-only [bitget:bitget_detail_plan]. Account endpoints change margin mode and leverage [bitget:bitget_detail_account]; order/fill queries and position state are documented [bitget:bitget_detail_trade] [bitget:bitget_detail_position]. `clientOid` is a query handle, but an exact duplicate-request guarantee is not established. The REST guide literally lists distinct “Read-Only permission,” “Trade permission,” “Transfer permission,” and “Withdraw permission,” allowing the scoped Read+Trade architecture without Withdraw; it only explicitly requires a whitelisted IP for withdrawal, so trading-key IP binding remains unverified [bitget:bitget_docs_rest_api]. Place-order is limited to 10 requests/s/UID; market data endpoints commonly state 20/s/IP [bitget:bitget_detail_trade] [bitget:bitget_detail_market]. A Classic demo REST guide is available [bitget:bitget_docs_demo_rest]. A current status/maintenance feed was not verified.

No 403 occurred on the scoped Bitget public API probes. A separate `docs.bitget.com` tunnel returned 403, while the current official `www.bitget.com/docs/...` pages succeeded; the former is not used to infer API blocking. Ordinary GitHub CI accessibility, account eligibility and live trading safety still require separate checks. No strategy signal, order, account, P&L or private credential was touched.
