# Execution metadata compatibility audit — same agent as historical data engineer

I performed this execution-auditor role as **the same agent** who wrote `reviews/historical_data_engineer.md` and the other scoped audits; these files do not represent independent agents. I inspected frozen metadata, contract and runner code without changing implementation or reading/running financial outcomes.

The core uses `USDT_LINEAR_PERPETUAL` as the exact contract type and `proven_tick_epoch` as its price-grid gate (`scripts/machine_strategy_v3_contracts.py`, lines 31, 122–175). A usable row needs matching symbol/contract, unique nonoverlapping coverage at each event, positive `Decimal` tick, literal boolean `verified`, integer `effective_from`/`effective_until`/`known_at`/`source_known_at`/`effective_proof_known_at`, a nonzero 64-character source digest, and all known times at or before the decision. Failure returns `WAIT_HISTORICAL_TICK_METADATA`. `executable_plan` calls this at the decision; it floors LONG entry, ceils SHORT entry, and puts protective stops one tick strictly outward from the raw boundary (`scripts/machine_strategy_v3_contracts.py`, lines 497–513, 548–570). Thus a tick error changes entry/stop/target geometry, not just formatting. The current `TICK_EPOCHS.json` has `verified_core_epochs=[]`; no notice claim can be passed as an executable row.

The guarded runner's `validate_historical_epochs` requires complete development coverage `[START,END)` (`START=2023-01-01T00:00:00Z`, `END=2025-12-05T23:30:00Z`), source and effective-proof paths under `docs/`, both byte hashes pinned in the freeze manifest, `VERIFIED_COMPLETE_INTERVAL`, and core validation at epoch boundaries (`scripts/machine_strategy_v3_guarded_runner.py`, lines 221–265; `scripts/original_v1_1_financial_data.py`, lines 16–18). It does not determine from raw bytes whether the evidence actually proves implementation or unchanged continuity; that remains an external evidence-review responsibility. Its validator starts at `START`, whereas `load_primary` reads from `WARMUP=2022-01-01T00:00:00Z` (`scripts/machine_strategy_v3_historical_adapter.py`, lines 61–113). The **recovery gate requires 100% verified warmup as well as development coverage**, so the gate's own coverage map/QA must explicitly check warmup; a passing runner development validator alone would not satisfy this task. This is a scope gap in what that validator proves, not evidence of a current bypass because no verified rows exist and no financial authorization is present.

For the notice-only hypothetical grids, exact raw-OHLC divisibility passed all 2022 bars and post-claim bars but failed one BTC bar/one cell and four ETH bars/six cells immediately before the claimed changes; see the historical-data review for exact fields and file hashes. `observe_m15_bar` also checks both endpoints of an M15 bar resolve to the same tick epoch and rejects off-grid OHLC/plan values (`scripts/machine_strategy_v3_contracts.py`, lines 709–743). Therefore simply promoting notice tick values would create an unresolved contradiction at the frozen source rows; rounding those rows is forbidden. Candidate agreement elsewhere cannot authenticate a price filter or permit historical execution.

**Finding:** current artifacts are correctly blocked by absent verified rows. Before readiness can be promoted, require independently proved nonoverlapping epochs for the entire 2022 warmup and declared development interval, authenticated source/effective-proof hashes, truthful causal known-at times, and exact-Decimal zero-contradiction OHLC compatibility against each proved epoch. Preserve STOP while any of those remain open.
