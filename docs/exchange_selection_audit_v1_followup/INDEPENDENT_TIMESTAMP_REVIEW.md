# Independent review of Kraken CI timestamp semantics

Reviewer: `/root/exchange_final_independent_reviewer_v1`. This is an additive post-freeze assessment of `TIMESTAMP_SEMANTICS_NOTE.md`, not an amendment to the sealed exchange audit. The original freeze still verifies with `--resume-existing` at SHA-256 `06556298d9f8041c493af5225740425cdfc51807566a322e2dd86f944b9c24d5` and retains `EXCHANGE_SELECTION_AUDIT_FROZEN_PASS`.

The finding is real. The frozen builder leaves the Kraken CI `stamp` unset and substitutes each receipt's `response_completed_at` as normalized `time_utc`. The four hash-retained raw responses contain distinct ISO `serverTime` values. For example, BTC receipt `6aaa168e47d606679a03ae6b` has raw `serverTime=2026-10-13T06:39:00.732Z` while its normalized `time_utc` is receipt completion `2026-10-13T06:39:00.860645+00:00`. The payload has no separate book-event timestamp, so even the response's `serverTime` must be labeled as exchange **server response time**, not asserted as the exact order-book event time.

In a scratch-only substitution of the four CI times with their raw `serverTime` values, Kraken still has five distinct retained book samples for BTC and five for ETH, ten distinct source IDs, no newly rejected or deduplicated sample, the same numerical book estimates, and the same `scoring_usable=false` result. Kraken's book-size units are unproven, so its execution cost and liquidity criteria already score zero. Its research score, execution score, hard eligibility, the Bitget/BloFin primaries, and the disclosed Kraken/KuCoin secondary tie and sensitivity therefore do not change. This timestamp-label error does **not** overturn the conditional architecture PASS. It does preclude treating these frozen normalized Kraken CI `time_utc` fields as exchange event times for causal or financial use.

The next Unified Exchange Layer gate must store exchange server time, any actual book-event time, request start, receipt completion, retrieval time and `known_at` as separately named, sourced fields. An absent event timestamp stays unknown. The adapter should parse Kraken's ISO `serverTime`, preserve the receipt clock, and test timestamp-kind and `known_at` causality before prospective capture or financial replay. Any corrected diagnostic belongs in a new version with pinned source bytes; the v1 freeze remains immutable. No private API, orders, strategy outcomes, financial run, OOS clock, PAPER or LIVE activation is involved.

**Independent verdict: conditional architecture PASS remains defensible; timestamp semantics require a narrow corrective adapter/version gate before causal use.**
