# Автоматические SL и три TP для офлайн BACKTEST → SHADOW

Автоматический подбор включается явно через `--auto-levels`. Это
экспериментальная машинная формализация OB/HTF POI, а не завершённая проверка
соответствия первичным материалам. Режимы BACKTEST и SHADOW используют один
закрытосвечной алгоритм. SHADOW здесь работает по историческим CSV: текущий
рыночный поток и исполнение ордеров не подключены. `trade_entry_allowed=false`
сохранён у сигналов и виртуального портфеля.

## Запуск и API

В PowerShell из корня обновлённого проекта:

```powershell
$env:PYTHONPATH = "src"
py scripts/run_strategy_replay.py --symbols BTCUSDT --mode BACKTEST --htf 60 --ltf 5 --bars 288 --warmup-bars 576 --auto-levels --report-root data/reports/btc_auto_backtest
```

Для офлайн SHADOW используйте те же параметры с `--mode SHADOW` и отдельной
папкой отчёта. CLI запрещает одновременные `--auto-levels` и
`--qualified-levels FILE.json`. Без этих параметров вход по-прежнему ждёт
явно квалифицированных уровней. Нестандартные пороги OB требуют `--auto-levels`.

API принимает `AutoLevelPolicy` в аргументе `auto_level_policy` функции
`evaluate_snapshot`. Автоматическая политика и непустая карта
`qualified_levels` взаимоисключающие. Пороги по умолчанию:

| Поле API | Параметр CLI | Значение | Статус правила |
| --- | --- | --- | --- |
| `min_body_fraction` | `--min-ob-body-fraction` | `0.6` | `BACKTEST_PARAMETER` |
| `min_engulf_body_ratio` | `--min-engulf-body-ratio` | `1.0` | `BACKTEST_PARAMETER` |

Численная сила импульса не определена в исходных материалах. Эти пороги нужно
исследовать, а не считать подтверждёнными источником или доходностью.

## Что требуется для автоматического SL

Используются только закрытые непрерывные HTF/LTF свечи, доступные на `as_of`.
Анализ структуры — `SOURCE_CONSERVATIVE`; техническое восстановление прежнего
тренда не открывает вход. Сначала нужны завершённый HTF SFP, причинно более
поздний LTF BOS в ожидаемом направлении и готовый переход в противоположную
структуру с корректной OTE.

Подбор LTF Order Block дополнительно требует:

- соседние закрытые свечи A/B после BOS; B поглощает A в направлении сигнала и
  проходит заданные пороги тела;
- положение пары в подтверждённом структурном импульсе и пересечение зоны OB
  с готовой зоной OTE;
- наблюдаемое снятие структурной ликвидности свечой A;
- расположение OB в существовавшей до A HTF трёхсвечной gap-POI того же
  направления и её первую реакцию свечой A;
- LTF трёхсвечный IMB; эта версия всегда требует IMB;
- свежий OB для первого теста: уже протестированную зону нельзя автоматически
  повторно квалифицировать.

HTF gap-POI — явная экспериментальная опора: сам факт разрыва не доказывает
полную source-квалификацию POI. Свежесть поддерживающей HTF зоны проверяется
до её первой реакции; эту реакцию нельзя одновременно трактовать как
предшествующее потребление зоны. Неоднозначность обязательности IMB в исходном
тексте остаётся открытой; использование только кандидатов с IMB — выбранное
консервативное ограничение реализации.

SL берётся на экстремуме A без придуманного буфера. Геометрический способ
сохраняет имя `SOURCE_OB_EXTREME`, но автоматический выбор самого OB остаётся
экспериментальным. Для LONG SL должен быть строго ниже всей зоны входа, для
SHORT — строго выше. Иначе сетап остаётся без автоматического входа.

## Как выбираются TP1/TP2/TP3

Нужны три разные непересекающиеся свежие HTF gap-POI противоположного
направления, полностью за зоной входа в направлении прибыли. Проверка свежести
цели рассматривает последующие свечи после рождения зоны и выполняется на
текущий `as_of`.

Зоны сортируются по достижимости цены. TP1 находится на ближней границе
первой зоны — экспериментальной FTA; TP2 и TP3 — на ближних границах следующих
двух зон. Для LONG цели строго возрастают, для SHORT строго убывают. Нехватка
трёх подходящих зон блокирует вход: цели не заменяются множителями риска и
не создаются делением одной POI на три части.

Выбор жадный: после ближайшей зоны перекрывающиеся с уже выбранными зоны
пропускаются как дополнительные описания того же ценового участка. Следующая
цель берётся из ближайшей оставшейся непересекающейся зоны. Поэтому TP2/TP3
могут оказаться дальше второй/третьей зоны в исходном списке gap-кандидатов.

Выбор gap-POI, трёх целей и их границ — экспериментальная политика, а не
подтверждённое источником расширение единственной первой opposing-POI/FTA.
Виртуальное сопровождение сохраняет TP 40/30/30 и перенос остатка после TP1
в безубыток с комиссиями и проскальзыванием.

## Причинность, состояния и отчёт

Готовность появляется только после доступности всех подтверждений, включая
третью свечу IMB, структуру, HTF POI и цели. `levels_known_at` сохраняет время
доступности уровней; решение наблюдается на текущем закрытии, без переноса
назад на свечу формирования. Виртуальный вход возможен со следующего открытия
и только при выполнении правил портфеля и зоны входа.

Автоматическая политика маркируется
`AUTO_NORMALIZED_EVIDENCE_PENDING_SOURCE_REVIEW`. Каждый сигнал экспортирует
`level_policy`, `level_evidence`, `level_blocking_reasons` и
`levels_known_at`. Отчёт `summary.json` содержит параметры
`automatic_level_policy`, изменения сигналов, причины блокировок и хеши входных
CSV. Статистика сигналов относится к последнему состоянию каждого уникального
сетапа. `input_code_hashes` сохраняет SHA-256 исходников, CLI, реестра правил
и метаданных проекта, чтобы связывать прогон с конкретной реализацией.
`decisions.jsonl` содержит решения виртуального портфеля;
`fingerprint.sha256` позволяет сравнить повторные прогоны при одинаковых входах
и параметрах.

Неполное подтверждение даёт `WAITING_FOR_AUTO_LEVELS` с конкретной причиной.
Повторное вычисление может отозвать ранее готовые уровни при утрате свежести
POI. Новый ожидающий сигнал удаляет прежнюю заявку того же ID из очереди на
текущем закрытии; прошлое решение на открытии этой свечи не пересчитывается.
Уже открытая виртуальная позиция продолжает сопровождаться своими уровнями.

## Что пока не подтверждено

Оригинальные PDF в рабочем архиве отсутствуют; их повторная проверка остаётся
отдельной задачей. Gap как HTF POI, машинное поглощение, численная агрессия,
первый тест и три цели требуют проверки по графикам и независимой оценки
параметров. Range clarity остаётся отдельным ограничением. Ноль виртуальных
сделок допустим: отсутствие квалификации не исправляется ослаблением правил
ради счётчика входов.

Виртуальные результаты не учитывают funding, ликвидацию, биржевые ограничения
и точное исполнение реальных заявок. Повторяемость и программные проверки
не устанавливают доходность. Реальные ордера, private API и интеграция с
production в этот этап не входят.
